# ADR-0018: Add a generator app that owns the pets and building manuals dataset

- **Status:** accepted
- **Scope:** system (a new app and a new shared dataset)
- **Date:** 2026-11-20
- **Related:** [idea 0001](../../ideas/0001-manual-ontology-assistant.md), [ADR-0010](0010-monorepo-of-loosely-coupled-applications.md), [ADR-0013](0013-shared-data-through-owned-datasets-and-contracts.md), [ADR-0016](0016-commit-or-ignore-each-data-folder.md)

## Context

Idea 0001 needs a small, controlled corpus of user manuals to build and test an AI assistant and an ontology builder: a dog owner's manual, a cat owner's manual and the house rules of a set of buildings with a shared inner yard. The corpus contains quality issues planted on purpose (a gap, a terminology drift and a contradiction), so that the assistant can be tested against known answers.

The manuals were generated by an LLM from the user's instructions and placed in `data/user-manuals-pets-and-house-rules/`. ADR-0013 requires every shared dataset to have exactly one owning app, its only writer, and a contract in `libs/contracts/<dataset>/`. No app existed yet. The instructions that produced the manuals also had to live somewhere, so that the corpus can be regenerated or extended without breaking the planted issues.

## Decision

We will add the app `generate-pets-and-building-user-manual`. Its only content is the collected generation instructions: the user's requests, quoted word for word, and the conventions used during generation. It owns the dataset `user-manuals-pets-and-house-rules`, whose contract (`libs/contracts/user-manuals-pets-and-house-rules/`) fixes the layout:
- three manual folders;
- one Markdown file per chapter;
- a folder for each chapter that has sub-chapters;
- a level-1 heading in every file that carries the chapter numbers.

The dataset is committed to git (ADR-0016): it is small, contains no personal data, and every fresh clone needs it for tests.

The answer key (planted issues and expected answers) stays outside the dataset, in `docs/research/notes/pet-manuals-corpus/`, so that apps reading the dataset cannot see it.

## Alternatives considered

| Option | Pros | Cons | Why not chosen |
|--------|------|------|----------------|
| Keep the manuals in `docs/research/` | No new app or contract | The future assistant would read data from documentation; no contract for readers | Breaks the "data through datasets" rule (ADR-0013) |
| Make the future assistant app the owner | One app fewer | The assistant would own the data it is tested against, mixing test data with product; the assistant doesn't exist yet | Ownership should sit with whatever produces the data |
| A generator app with code that calls the Claude API | Reproducible, automated regeneration | Code without a spec; the manuals are a one-off corpus that is edited by hand as often as regenerated | Not needed now; can be added later by a spec for this app |
| Put the answer key inside the dataset | Everything in one place | Readers under test could read the expected answers | Spoils the tests |

## Consequences

- **Positive:** the dataset has an owner and a contract before any reader exists. The instructions that produced it are versioned next to its owner, and the planted issues are written down as rules the generator must keep.
- **Negative / trade-offs:** the app contains no code, so "regenerating" means an LLM session follows the instructions by hand. Nothing enforces the contract layout automatically.
- **Follow-up:** done in this change:
  - the app and the dataset are registered in the root `components.json`, and the system map is regenerated;
  - the contract's format and guarantees are written;
  - the app's `architecture.md`, `README.md` and `CLAUDE.md` describe its contents.

  Still open: the apps of idea 0001 must add the dataset to their `reads` when they are scaffolded.
