# Ontology, Enterprise Knowledge Graph and Controlled Vocabulary Governance Processes

Research notes collected 2026-11-20 for the planned "OntologyBuilder" app: users review, include, exclude or correct components an LLM proposes and author missing content; a domain admin approves or rejects; the app flags contradictions, gaps and ambiguity; a final ontology is built and released.

Method: about 18 web searches and fetches. Most findings come from primary documentation (OBO Foundry principles, ROBOT docs, GO docs, TopBraid EDG docs, PoolParty docs, Wikidata policy pages). Some come from search-result summaries of those pages, not full reads; these are marked "(summary)" where it matters.

## Roles: owner/steward, domain expert, editor, curator, reviewer, consumer; RACI patterns

### Takeaway
Every mature tool and framework keeps the people who propose or edit content apart from the people who approve and publish it. Typical role sets are Editor → Validator/Reviewer → Publisher (VocBench), editor/manager plus a governance role such as data governor or business steward (TopBraid EDG), and user → reviewer/administrator (PoolParty). Data governance frameworks add an owner who holds approval authority and stewards who do the day-to-day work. None of the sources publishes a ready-made RACI matrix for ontologies; one has to be built from these role splits.

### Cited Findings
- VocBench 3's default access policy defines Administrators, Ontology editors, Term editors (Terminologists), Validators and Publishers. Roles can be customised. Editors' changes are tracked and stored until a content validator approves them, so "different roles enforce the separation between responsibilities" — [VocBench 3, Semantic Web Journal](https://semantic-web-journal.net/content/vocbench-3-collaborative-semantic-web-editor-ontologies-thesauri-and-lexicons-1) (summary)
- VocBench describes a formal life cycle of concepts/terms from proposal to deprecation: a guest proposes a concept, a validator approves it, a publisher publishes it — [VocBench 3 insights slides (2017)](https://www.slideshare.net/CIARD_AIMS/vocbench-3-some-insights-on-the-forthcoming-release) (summary)
- A 2025 VocBench user-list reply warns that giving validation rights to an editing role makes validation too broad, because that role could then validate every user's actions and not only its own. Separate predefined roles are recommended instead — [vocbench-user group](https://groups.google.com/g/vocbench-user/c/Wv12FdfG07U) (summary)
- TopBraid EDG: permission levels are viewer, editor and manager, and they apply to both the production copy and workflow working copies. Workflow templates can grant editor or manager rights by governance role. Transitions can require a governance role or a minimum permission level (`teamwork:requiredTagPermissionRole`). Whoever starts a workflow becomes manager of its working copy — [TopBraid EDG 8.4 Workflows](https://www.topquadrant.com/doc/8.4/user_guide/workflows/index.html); [EDG workflow template guide](https://www.topquadrant.com/doc/8.4/quick_start_guides/edg_workflow_template/index.html)
- In EDG examples, "Approve changes" is limited to `edg:dataGovernor`, while the sample glossary template gives approval and acceptance into production to `edg:businessSteward` — [EDG workflow template guide](https://www.topquadrant.com/doc/8.4/quick_start_guides/edg_workflow_template/index.html); [EDG 9.2 workflow_samples.ttl](https://www.topquadrant.com/doc/9.2/_downloads/0588f9de404d08baef248efd1e244159/workflow_samples.ttl)
- PoolParty: a regular user can hand a draft concept to another user to complete it, or send it to a reviewer who has the administrator role. The reviewer can approve, reject (with a note) or reassign the draft to another user or reviewer, for example to get clarification — [PoolParty Approval Workflow – Workflow in Action](https://help.poolparty.biz/en/user-guide-for-knowledge-engineers/enterprise-features/the-workflow-dashboard/approval-workflow/workflow-in-action.html)
- WebProtégé gives each named user read, write or comment rights, and an ontology is public or private — [WebProtégé release notes](https://protegewiki.stanford.edu/wiki/WebProtegeReleaseNotes) (summary)
- Gene Ontology: anyone can request a change, preferably through the go-ontology GitHub issue tracker; ontology editors process the requests. A new-term request needs a label, a definition, a parent and at least one reference (PMID, ISBN or DOI). Synonyms and cross-references are optional. GO asks for one ticket per term unless the terms are related — [GO: Contributing to GO terms](https://geneontology.org/docs/contributing-to-go-terms/)
- DAMA-DMBOK (secondary sources) names four steward types: executive, business, technical and coordinating. A data owner is "a type of Business Data Steward with approval authority" for their domain. Owner maps to accountability and approval authority; steward maps to day-to-day definition and metadata curation. Stewardship must be business-led: IT cannot set business meaning on its own. Coordinating stewards represent groups of business and technical stewards. DAMA recommends a federated (hub-and-spoke) model for large enterprises — [open-exam-prep CDMP: Data Stewardship](https://open-exam-prep.com/study-guides/cdmp/data-governance-b/data-stewardship); [EWSolutions: Data stewardship roles](https://ewsolutions.com/data-stewardship-roles-a-complete-guide); [GCcollab wiki: Data Steward](https://wiki.gccollab.ca/Data_Steward). These are secondary summaries, not the DMBOK text, and they differ on the number of roles (some list nine).

### Inferences
- A minimal role model for OntologyBuilder: **Contributor/Editor** (domain user who reviews, includes, excludes or corrects LLM proposals and writes new content), **Reviewer/Validator** (optional peer review), **Domain admin** (approval authority; corresponds to data owner, EDG data governor or business steward, PoolParty reviewer/admin), **Publisher/Release manager** (often the same person as the domain admin in small teams), **Consumer** (read only). The LLM acts as a non-human "proposer" agent, comparable to a VocBench guest or PoolParty's "Suggested" source.
- Suggested RACI (inferred, not sourced): proposing a component — R: LLM/Contributor, A: Domain admin. Correcting or authoring — R: Contributor. Approving — R/A: Domain admin, C: Reviewers. Release — R: Publisher, A: Domain admin, I: Consumers.
- Following VocBench's warning, a person should not be able to approve their own edits (four-eyes rule), or the app should at least make self-approval a visible, configurable policy.

### Gaps
- No published RACI matrix specific to ontology governance was found.
- Full DAMA-DMBOK2 text was not consulted; role details come from secondary sources.

## Lifecycle and status models for terms and axioms

### Takeaway
Status models in use share one spine: **Draft/Proposed → (Under review) → Approved/Standard → Deprecated/Superseded/Retired**. OBO adds strict rules for obsoletion: never silently delete or redefine a term; mark it `owl:deprecated`, give `term replaced by` or `consider`, and announce it in advance. ISO/IEC 11179-6 offers the most detailed registration ladder. W3C `vs:term_status` is a lightweight, schema-level alternative.

### Cited Findings
- **OBO Principle 19 (Stability of Term Meaning):** a term's definition must keep the same referents. If a change would alter them, create a new term with a new IRI. Minor clarity edits are allowed. To obsolete a term: set `owl:deprecated true`; prefix the label with "obsolete "; remove all logical axioms; remove or replace every use elsewhere. Recommended: `term replaced by` (IAO:0100001) for exact replacements and `oboInOwl:consider` for inexact ones. Optional: an obsolescence reason (IAO:0000231) and an "OBSOLETE. " prefix on the definition. Obsoletions should be announced in advance. Grounds: the definition misses its targets, or is too vague, too restrictive or misused. The OBO Dashboard enforces this automatically: it is an error if the label prefix is missing, if the deprecation flag is missing, or if an obsolete term still has axioms or is referenced — [OBO Foundry Principle 19](https://obofoundry.org/principles/fp-019-term-stability.html)
- OBO Academy: use `consider` when there is no exact replacement but existing terms might suit. Some ontologies give advance notice with a 'scheduled for obsoletion on or after' annotation — [OBO Academy: obsolete term](https://oboacademy.github.io/obook/howto/obsolete-term) (summary)
- Mondo: merges use `term replaced by` with obsolescence reason "terms merged". When the replacement lives in another ontology (for example HPO), use `consider`, not `term replaced by` — [Mondo: merging and obsoleting](https://mondo.readthedocs.io/en/latest/editors-guide/merging-and-obsoleting/) (summary)
- The GO obsoletion procedure starts by checking whether the term or any of its children are used in annotations — [GO: Obsoleting an Existing Ontology Term](https://go-ontology.readthedocs.io/en/stable/ObsoleteTerm.html) (summary). GO also documents how to restore an obsolete term — [GO wiki: Restoring an Obsolete Term](https://wiki.geneontology.org/Restoring_an_Obsolete_Ontology_Term)
- **ISO/IEC 11179-6 registration statuses** (as worded by registries that implement it): *Candidate* (proposed for progression; accepted onto a committee's work program) → *Recorded* (all mandatory metadata attributes complete) → *Qualified* (a committee recommends it for approval as a standard) → *Standard* (sufficient quality and broad interest) → *Preferred Standard* (the recommended one among similar standards) → *Superseded* (replaced by another standard) / *Retired* (no longer recommended for use). The current edition is ISO/IEC 11179-6:2023 — [AIHW METEOR: Registration statuses](https://meteor.aihw.gov.au/content/752877); [NSW metadata: statuses](https://www.metadata.nsw.gov.au/help/page/whats_are_statuses); [ISO/IEC 11179-6:2023 catalog](https://standards.iteh.ai/catalog/standards/iso/dd7f4da6-41bb-4592-bab6-3338a8f37ba9/iso-iec-11179-6-2023)
- **PoolParty concept statuses:** Draft (created, edited or imported), Suggested (submitted through the suggest API), Approved (set by an administrator), Deprecated (removed by an administrator; its triples stay visible on the dashboard). Any edit returns an approved concept to Draft. One docs version says concept deletion is not yet covered by the approval process. The workflow is an Enterprise-tier feature — [PoolParty Approval Workflow](https://help.poolparty.biz/en/user-guide-for-knowledge-engineers/enterprise-features/the-workflow-dashboard/approval-workflow.html); [Graphwise copy](https://help.graphwise.ai/en/graph-modeling/thesaurus/the-workflow-dashboard/approval-workflow.html)
- PoolParty also has a separate "Suggested concepts workflow" for concepts proposed from outside — [PoolParty: suggested concepts workflow](https://help.poolparty.biz/en/user-guide-for-knowledge-engineers/expert-features/the-workflow-dashboard/suggested-concepts-workflow.html)
- **TopBraid EDG** tracks status per change set (workflow), not per term: Uncommitted → Under review → Approved → Committed. "Request further changes" moves the set back to Uncommitted. Older 7.x versions call the review state "Frozen for Review". Statuses are `teamwork:TagStatus` instances and transitions are configurable — [EDG workflow template guide](https://www.topquadrant.com/doc/8.4/quick_start_guides/edg_workflow_template/index.html); [EDG 7.2 Workflow status and transition tab](https://www.topquadrant.com/doc/7.2/user_guide/workflows/workflow_status_and_transition_tab.html)
- **W3C `vs:term_status`** (used for SKOS's own schema terms): 'unstable', 'testing', 'stable', plus 'archaic' added in 2009; the list is open-ended and each project interprets it. 'deprecated' was seen in use but never formally added — [W3C Vocabulary Status note](https://www.w3.org/2003/06/sw-vocab-status/note); [W3C SkosDev/SchemaManagement](https://www.w3.org/wiki/SkosDev/SchemaManagement)
- **Wikidata property creation:** a proposal must be discussed on the Property proposal page first. Once there is agreement, the status is set to "ready". A property creator or administrator can create the property one week after the proposal was made — [Wikidata: Property proposal](https://www.wikidata.org/wiki/Wikidata:Property_proposal). A secondhand comment describes a 7-day minimum with majority support. A 2016 RFC debated barring participants from creating properties they had discussed; adoption is unconfirmed — [Wikidata RFC: Reforming the property creation process](https://www.wikidata.org/wiki/Wikidata:Requests_for_comment/Reforming_the_property_creation_process)

### Inferences
- OntologyBuilder could use **per-component** statuses such as `proposed` (LLM) / `draft` (human-authored) → `included` / `excluded` (user triage) → `under_review` → `approved` / `rejected` → after release `deprecated` (with `replaced_by` / `consider` / reason). It could also use **per-change-set or per-release** statuses in the EDG style (working copy → under review → approved → committed/released).
- "Excluded" (user triage) and "rejected" (admin decision) should be separate and should keep their rationale, like PoolParty's rejection note, so an LLM does not propose the same thing again.
- Following PoolParty's rule, any edit to an approved component should send it back for review.
- Released components should never be hard-deleted (OBO P19); deprecation keeps their IRIs resolvable.

### Gaps
- No primary ISO 25964 text on thesaurus maintenance or status was found (the standard is paywalled). ISO 25964-1 maintenance guidance remains unverified.
- No status model was found for **individual axioms** as opposed to terms. OBO handles axioms through PR-level review, not per-axiom status.
- GO's issue templates and labels were not confirmed from the page fetched.

## Change management: versioning, release cycles, change logs, deprecation policies, diff tools

### Takeaway
Releases should be immutable, versioned artifacts (`owl:versionIRI`, as a date or a semantic version), built by a pipeline (ODK/ROBOT). Change logs are produced by diffing releases: ROBOT diff and Bubastis at axiom level, ecco at axiom and concept level. Deprecation follows OBO obsoletion with advance notice.

### Cited Findings
- **OBO Principle 4 (Versioning):** besides the IRI of the current release, every official release must have a unique version IRI that resolves to that exact artifact. Version identifiers are dates (YYYY-MM-DD) or numbers such as semantic versions. The OBO Dashboard checks that a version IRI is present — [OBO Foundry Principle 4](https://obofoundry.org/principles/fp-004-versioning.html); [Versioning automated check](https://obofoundry.org/principles/checks/fp_004)
- Dated version IRIs follow the pattern `/obo/<ont>/releases/YYYY-MM-DD/<artifact>` — [public-semweb-lifesci 2017 thread](https://lists.w3.org/Archives/Public/public-semweb-lifesci/2017Jan/0019.html) (summary)
- **ODK release workflow:** make sure all PRs are merged and the ODK image is current; run the release from `src/ontology`, which builds every release target (OBO, OWL, JSON and variants) into the release directory; review the release; merge to main; create a GitHub release — [OBO Foundry COB: ODK Release Workflow](https://obofoundry.org/COB/odk-workflows/ReleaseWorkflow/)
- Recent ODK versions manage `qc.yml` and include a release-diff action that can post diffs as comments on pull requests — [ODK releases](https://www.github.com/INCATools/ontology-development-kit/releases) (summary)
- The ENERO/OEO Foundry requires versioning workflows that document the changes in each version, publication dates and version numbers, with `owl:versionIRI` — [OEO Foundry: version principle](https://oeofoundry.github.io/OEOFoundry/principles/5_version) (summary)
- **ROBOT diff** compares two ontologies, ignores differences that come only from file structure, and writes added and removed axioms (default OWL Functional syntax) — [ROBOT diff](https://robot.obolibrary.org/diff)
- **Bubastis** detects asserted logical differences between two OBO/OWL files (for example two versions) and writes plain-text or XML reports. EBI hosts a web version — [EBISPOT/bubastis](https://github.com/EBISPOT/bubastis)
- **ecco** (University of Manchester) is a hybrid structural and semantic OWL diff at axiom and concept level, available as a CLI and a web app — [ISWC 2013 demo paper](https://ceur-ws.org/Vol-1035/iswc2013_demo_13.pdf) (summary)
- ROBOT diff and Bubastis both work as set-based diffs of OWL axioms. That is precise but "at a lower level than how many ontology developers conceive of changes". This motivates KGCL, a change language for ontologies and knowledge graphs — [KGCL: A Change Language for Ontologies and KGs (arXiv 2409.13906)](https://arxiv.org/pdf/2409.13906)
- WebProtégé records every edit, grouped into revisions with description, author and timestamp. Revisions can be reverted or downloaded, and a commit can carry a message — [WebProtégé paper, PMC3041389](https://pmc.ncbi.nlm.nih.gov/articles/PMC3041389) (summary)

### Inferences
- OntologyBuilder should give each release a version IRI and a semantic or date version. It should generate a human-readable change log from the diff against the previous release (added, changed, deprecated components, ideally in KGCL-like change types rather than raw axioms), and keep an append-only edit history like WebProtégé revisions.
- Semantic-version mapping (inferred): patch = labels, definitions, synonyms; minor = new terms; major = deprecations or changes in meaning. Note that OBO P19 says a change in meaning should be a new term, not an edit.

### Gaps
- No authoritative community standard for semantic versioning of ontologies (what counts as major, minor or patch) was found.
- Current maintenance status of ecco and Bubastis was not verified.

## Quality gates: automated checks, review of LLM content, human-in-the-loop, provenance, confidence

### Takeaway
Mature pipelines gate merges and releases on automated QC: reasoner consistency (ELK/HermiT through ROBOT), `robot report` with severity levels, where ERROR blocks a release, `robot verify` with custom SPARQL, and optionally SHACL conformance before commit (TopBraid EDG). OOPS! adds a pitfall catalogue graded critical, important or minor. For LLM-generated content, the literature agrees that human review is required. A common pattern is to auto-accept high-confidence items and send low-confidence or ambiguous ones to experts. Provenance is usually modelled with PROV-O `prov:wasGeneratedBy` to a typed activity, but there is no standard vocabulary for LLM confidence.

### Cited Findings
- **ROBOT report:** runs QC SPARQL queries with levels ERROR (must be fixed before release, for example multiple labels), WARN (should be fixed soon, for example an inferred equivalence to another named class) and INFO (cosmetic, for example a lowercase definition). By default it exits 1 if there are ERRORs, which makes it a release gate; `--fail-on WARN` or `none` changes the threshold. A custom profile can disable checks or add `file:` queries that return `?entity ?property ?value` — [ROBOT report](https://robot.obolibrary.org/report)
- **ROBOT verify:** any result from a SPARQL QC query counts as a failure. Mondo runs `robot verify` with QC query files in its Makefile and uses ELK through ROBOT/owltools — [OBO Academy SPARQL tutorial](https://oboacademy.github.io/obook/tutorial/sparql); [Mondo quality control](https://mondo.readthedocs.io/en/latest/editors-guide/quality-control/). Custom checks are registered in the ODK config as `custom_sparql_checks` — [OBO Academy custom QC](https://oboacademy.github.io/obook/tutorial/custom-qc)
- The OBO/ODK editors' workflow: feature branch → pull request → review is required through GitHub branch protection → merge only after QC passes and approvals are given — [ODK Editors Workflow](https://berkeleybop.org/artificial-intelligence-ontology/odk-workflows/EditorsWorkflow/)
- **TopBraid EDG SHACL gate:** if `teamwork:tagShape` is set on a workflow template, Commit first forces a check that the working copy conforms to those SHACL shapes — [EDG workflow template guide](https://www.topquadrant.com/doc/8.4/quick_start_guides/edg_workflow_template/index.html)
- **OOPS!** (Poveda-Villalón et al., IJSWIS 2014): a pitfall catalogue built from an analysis of more than 693 ontologies, with structural, functional and usability-profiling dimensions. Importance levels: *critical* (affects consistency, reasoning or applicability; must fix), *important* (should fix), *minor* (fixing it improves organisation). It semi-automatically detects 32 pitfalls; domain-dependent pitfalls must be checked by hand; it does not repair anything — [OOPS! paper (RePEc)](https://ideas.repec.org/a/igg/jswis0/v10y2014i2p7-34.html); [OOPS! catalogue (DCMI LD4PE)](https://ld4pe.dublincore.org/learning_resource/oops-catalogue-of-common-pitfalls/) (summary)
- **LLM plus human in the loop:**
  - LLMs can reduce the human effort in building knowledge graphs, but a human-in-the-loop evaluation of generated KGs is recommended — [From human experts to machines (arXiv 2403.08345)](https://arxiv.org/pdf/2403.08345)
  - Expert calibration for taxonomy alignment: high-confidence LLM predictions are accepted automatically and ambiguous cases are flagged for expert review. Reported F1 was 0.97 against a human benchmark of 0.68 — [arXiv 2506.08422](https://arxiv.org/pdf/2506.08422)
  - OE-Assist (2025): a study with 19 ontology engineers found that human performance *dropped* when the LLM gave wrong guidance, showing an efficiency/accuracy trade-off (automation bias) — [arXiv 2507.14552](https://arxiv.org/html/2507.14552v1)
  - IDEA2 (2026 preprint): competency questions extracted by an LLM go through co-creative expert review, and rejected questions are reworded until consensus — [arXiv 2604.01344](https://arxiv.org/html/2604.01344v1)
  - X-HCOME: LLM construction alternates with human comparison against gold standards, refinement and consistency checks — [arXiv 2512.14288](https://arxiv.org/pdf/2512.14288)
  - Persistent consistency and accuracy problems mean human oversight is needed when formalising — [arXiv 2508.20693](https://arxiv.org/pdf/2508.20693)
  - Ontogenia (Lippolis et al.) prompts LLMs to draft OWL from requirements; only cited secondhand — [CEUR-WS Vol-4085 paper18](https://ceur-ws.org/Vol-4085/paper18.pdf)
- **Provenance and confidence:** PROV-CRED extends PROV-O so that an LLM-generated triple points through `prov:wasGeneratedBy` to an activity typed by its enrichment method. It warns that raw scores (for example an LLM's self-reported 0.85 against a KGE score of 0.7452) are not on a common scale and need calibration — [PROV-CRED, CEUR-WS Vol-4293 paper67](https://ceur-ws.org/Vol-4293/paper67.pdf). SILKNOW models predicted values as `rdf:Statement` linked to a `prov:Activity`, with confidence in a project-specific property — [arXiv 2406.00423](https://arxiv.org/pdf/2406.00423). SSKG Hub: LLM drafts give coverage, but "standards-grade reliability requires human oversight and a controlled release process", with independent review and certification by several experts — [arXiv 2603.00669](https://arxiv.org/pdf/2603.00669)
- GO requires at least one literature reference for each new term — [GO contributing](https://geneontology.org/docs/contributing-to-go-terms/)

### Inferences
- Layered gates for OntologyBuilder: (1) **per component on save**: syntax and required fields (label, definition, parent, source reference as in GO); (2) **per change set before approval**: reasoner consistency/coherence, ROBOT-report-style lint with ERROR/WARN/INFO, SHACL shapes, OOPS!-style pitfalls, flags for duplicate labels or synonyms; (3) **release gate**: no ERRORs, no unresolved contradiction flags, every included component approved, version IRI set, change log generated.
- For each LLM proposal, store the model, prompt or run ID, source passages, timestamp and confidence as PROV-O (`prov:wasGeneratedBy`, `prov:wasAttributedTo`, `prov:wasDerivedFrom`). Record every human decision as its own activity with agent and rationale. Treat LLM confidence as uncalibrated, so use it for sorting and triage, not for auto-approval, unless it has been calibrated.
- Because of the OE-Assist automation-bias finding, the review UI could show the evidence before the LLM's verdict and could sample auto-accepted items for audit.

### Gaps
- The W3C SHACL and PROV-O specifications were not fetched directly; usage is cited from tools and papers.
- No benchmark was found for how well reasoner and OOPS! checks catch LLM-specific errors.

## Enterprise governance practices: DAMA-DMBOK, taxonomy governance (PoolParty, TopBraid EDG), knowledge graph governance

### Takeaway
Enterprise tools put governance into **isolated working copies with approval workflows** (EDG) or **concept-level approval dashboards** (PoolParty), with roles taken from data governance (steward, governor, owner). DAMA-DMBOK adds the organisational layer: a business-led stewardship model in which owners hold approval authority, and federated hub-and-spoke structures for large organisations.

### Cited Findings
- EDG workflow changes are isolated from other workflows and from production until authorised users review, approve and commit them to the "production copy" — [TopBraid EDG 8.4 Workflows](https://www.topquadrant.com/doc/8.4/user_guide/workflows/index.html)
- EDG workflow templates define statuses, transitions and role requirements as RDF (`teamwork:TagStatus`, transitions with from and to status) — [EDG workflow template guide](https://www.topquadrant.com/doc/8.4/quick_start_guides/edg_workflow_template/index.html)
- The PoolParty workflow dashboard shows concepts by status; the API can read and change workflow status — [PoolParty Workflow Dashboard](https://help.poolparty.biz/en/user-guide-for-knowledge-engineers/enterprise-features/the-workflow-dashboard.html); [Using workflow status information](https://help.poolparty.biz/en/developer-guide/general-information-on-the-poolparty-api/using-workflow-status-information.html); [Project workflow services](https://help.poolparty.biz/en/poolparty-developer-guide/thesaurus---ontology-manager-api/project-workflow-services.html)
- DAMA-DMBOK role model and federated structure: see the Roles section — [open-exam-prep CDMP](https://open-exam-prep.com/study-guides/cdmp/data-management-organization) (secondary)
- Comparable glossary-governance tools (IBM InfoSphere, Talend Data Catalog) also define workflow roles for glossary assets — [IBM: Workflow roles of glossary assets](https://www.ibm.com/support/knowledgecenter/SSZJPZ_11.5.0/com.ibm.swg.im.iis.bg.doc/topics/c_workflow_roles.html?lang=en); [Talend: Workflow process options](https://help.qlik.com/talend/en-US/talend-data-catalog/Cloud/Subsystems/UserGuide/Content/Workflow-process-options.htm) (not read in detail)

### Inferences
- OntologyBuilder could combine both models: EDG-style **working copy / change set** (an LLM generation run plus user edits) that is reviewed and committed as a unit, and PoolParty-style **per-component status** inside it, so an admin can approve a batch or single items.
- Configurable workflow definitions (statuses, transitions, required role), as in EDG, would let different domains choose single- or two-stage approval.

### Gaps
- No vendor-neutral "knowledge graph governance" article of high quality was found within the search budget.
- Current-release EDG status names may differ from the 8.4 example.

## Conflict and contradiction resolution; handling multiple reviewers

### Takeaway
Conflict handling in practice is mostly **discussion plus a decision-maker**: threaded comments on entities (WebProtégé), GitHub issue and PR discussion (GO/OBO), reassigning for clarification (PoolParty), voting on change proposals (Collaborative Protégé), or community consensus with a fixed waiting period (Wikidata). Evidence from Wikidata shows that consensus often fails, so an explicit tie-breaking authority is needed. Logical contradictions are detected by reasoners and QC, not by people.

### Cited Findings
- WebProtégé supports threaded discussions on any ontology element, to discuss design or record provenance. Collaborative Protégé also allows threads on the whole ontology — [WebProtégé paper, PMC3041389](https://pmc.ncbi.nlm.nih.gov/articles/PMC3041389); [Collaborative Protégé](https://protegewiki.stanford.edu/wiki/Collaborative_Protege) (summary)
- Collaborative Protégé supports change proposals with two kinds of voting mechanism, and proposals can be rated and voted on (stored as annotation types). It was not confirmed that current WebProtégé keeps this — [Collaborative Protégé](https://protegewiki.stanford.edu/wiki/Collaborative_Protege); [PMC2656043](https://pmc.ncbi.nlm.nih.gov/articles/PMC2656043) (summary; 2008–2013 material)
- PoolParty: a reviewer can reassign a draft to another user or reviewer for clarification, or reject it with a note — [PoolParty Workflow in Action](https://help.poolparty.biz/en/user-guide-for-knowledge-engineers/enterprise-features/the-workflow-dashboard/approval-workflow/workflow-in-action.html)

- Wikidata: decisions to create properties are much faster than decisions to delete them, and more than half of controversial discussions end without consensus — [Agreeing and Disagreeing in Collaborative KG Construction (arXiv 2306.11766)](https://arxiv.org/html/2306.11766v3)
- GO: requesters follow progress and join the discussion with annotation team members in the GitHub tracker — [GO contributing](https://geneontology.org/docs/contributing-to-go-terms/)
- IDEA2: rejected items are reworded and re-reviewed until the experts reach consensus — [arXiv 2604.01344](https://arxiv.org/html/2604.01344v1)
- Automated contradiction detection: ROBOT report flags, for example, inferred equivalence between named classes (WARN), and reasoners detect inconsistency and unsatisfiable classes — [ROBOT report](https://robot.obolibrary.org/report); [Mondo QC](https://mondo.readthedocs.io/en/latest/editors-guide/quality-control/)
- A 2023 VocBench thread asked for two-step validation (editor proposes, business validator checks). It is a feature request, not a documented feature — [VocBench 3 search summary / vocbench-user](https://groups.google.com/g/vocbench-user/c/B61Bi_uCX1U) (summary)

### Inferences
- Suggested OntologyBuilder flow (inferred): a contradiction, gap or ambiguity flag (from the reasoner, QC, duplicate detection or the LLM) becomes an **issue** attached to the affected components. Reviewers comment in a thread and may vote. If they disagree, the domain admin decides and records a rationale; the issue cannot stay open past release (the release gate blocks it). Rejected items keep their rationale.
- For several reviewers: a configurable quorum (for example N approvals, or one admin approval), and a rule that any "request changes" blocks approval until it is resolved, like a GitHub PR review.

### Gaps
- No primary source was found that gives a formal multi-reviewer quorum or tie-break policy in ontology projects; GO/OBO rely on editor judgement.
- No source was found on how to detect "ambiguity" (as opposed to logical inconsistency) automatically; this is likely LLM-assisted and needs further research.
